# Needs-refix flag — user-driven "game updated" watermark (SHIPPED 2026-07-11)

After a game update, 3DMigoto mods bound to the game's asset HASHES break until re-fixed (hashes
regenerated by a fix tool). This surfaces a "may need re-fix" flag on those mods.

## Why it's a DATE APPROXIMATION, not automatic detection (decided 2026-07-11 — don't re-litigate)
Investigated: there is **no reliable automatic, game-free signal** for a game patch.
- The game's own version isn't read; the XXMI importer's version isn't tracked (`XxmiService` reads
  importer folders + `game_folder` path only).
- 3DMigoto's authoritative "hashes broke" signal is its **missing-hash log — only while the game runs**.

So the flag is a proxy: the USER marks the game updated; a mod is flagged if its last in-app fix
predates that mark. User chose this over (a) auto-detect via importer-core mtime (fragile/false-triggers)
and (b) not building it. Accepts false positives + needs user discipline; that's the honest ceiling.

## The two data points + the derivation
1. **Per-mod `lastFixedUtc`** — `ModFixService` stamps `metadata.fix.lastFixedUtc` on every successful
   fix (`StampFixedAsync` → `WriteFixMetadata`, a JsonNode merge that PRESERVES other fields like
   `metadata.remote`; best-effort — a stamp failure never fails the fix). `ModFixService` injects
   `IModRepository` (the same cross-module precedent `RemoteImportService` uses to write mod metadata).
2. **Per-profile `gameUpdatedUtc`** — `ProfileConfiguration.GameUpdatedUtc`, stamped/cleared via
   ProfileFacade IPC **`SET_GAME_UPDATED`** `{ profileId, clear? }` (in-facade: load config → set → save
   → emit `CONFIG_UPDATED`).
3. **Flag = pure FRONTEND derivation** (no new query/store/derived-data chain — `mod.metadata` is already
   on every list row via `ModMapper`, and the profile config is already loaded into `settingsStore`).
   `shared/utils/modFixRef.ts` `modNeedsRefix(metadata, gameUpdatedUtc)`: true iff a mod HAS a
   `lastFixedUtc` AND it's before the watermark. **Never-fixed mods are NOT flagged** (no basis — most
   mods ship pre-fixed; flagging all after an update = noise).

## Wiring
- Backend: `ProfileConfiguration.GameUpdatedUtc`; `ProfileFacade` `SET_GAME_UPDATED`; `ModFixService`
  `StampFixedAsync`/`WriteFixMetadata` (+ `IModRepository` ctor dep — updates any test that news it up).
- Frontend: `profileService.setGameUpdated`; `ProfileConfiguration.gameUpdatedUtc` type;
  `settingsStore.gameUpdatedUtc` + `setGameUpdated` (loaded in `settingsOperations.loadProfileConfig`);
  `modFixRef.ts`; **ModWorkSettingsTab** "Game updated" field (mark now / last-marked / clear);
  **ModList** row badge (`StatusTag` warning + tooltip), reads `useSettingsStore(s => s.gameUpdatedUtc)`.
- i18n: `mods.list.needsRefix`/`needsRefixHint`, `settings.profile.gameUpdate.*`, `common.clear` (en+cn).
- Tests: `ModFixMetadataTests` (WriteFixMetadata round-trip/preserve/overwrite/garbage),
  `modFixRef.test.ts` (parse + before/after/never/no-watermark).

The watermark surfaces where the setting lives (ModWorkSettingsTab, next to XXMI/launch); the flag
surfaces on the mod list. It is intentionally per-profile (each profile targets one game/importer).
